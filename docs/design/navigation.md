# Walking navigation experience

Navigation is the primary landing task in Explore/Navigate. The route form replaces discovery search and category chips while open; Explore remains available through Back. Weather and Transport remain secondary modes.

## Flow

1. Paste a shared Google Maps link, coordinates, or type a place in To.
2. Choose a result. From defaults to Current location, with GPS requested only when the user asks for a route. Both fields can be edited independently. Map selection and official station-level selection are contextual alternatives while editing a field.
3. Select Recommended, Shortest, or Barrier-free. Calculate the preferred route, then use Compare routes to load the two remaining profiles. Select an available result to update the map and journey. Language, source limitations, original directions and floor plans use progressive disclosure.
4. Start walking enables a GPS watcher and optional compass permission, a heading-aware marker, a smooth follow camera, approximate remaining distance and source instructions. Touching the map or using manual camera controls pauses camera following; Recentre resumes it. During guidance, the mobile location button also recentres using the existing GPS watcher rather than requesting a separate fix and overview flight. End stops the watcher and restores the planned route.
5. An off-route warning offers explicit recalculation from the current fix. A denied location permission, stale fix or poor accuracy is not presented as reliable guidance.

The Android link supplied on 17 October 2026 expands to a business/floor/address string and a Google place ID, without coordinates. The resolver preserves that label and offers official LandsD address candidates, prioritising an exact building-name match. It does not treat an unrelated Google page camera, or another business inside the same building, as the shared business location. Such candidates are building references: the business identity, floor and entrance are not independently verified. URLs with explicit place coordinates continue to resolve directly. Arbitrary URL proxying remains prohibited.

## Route comparison and preferences

The preferred profile is requested first. Compare routes expands the mobile sheet and loads only the missing profiles through the existing validated routing API. All comparison requests reuse the first result's resolved mapped endpoints, including a resolved assumed concourse, and the same directions language. The GPS origin is captured once for that comparison. Each profile has its own pending/error state and retry; failures never replace a valid selected route. Loaded choices can be selected without another request. Identical mapped paths are identified as such rather than presented as fabricated alternatives.

Cards show source distance/time estimates, recognised lift/stair/escalator/ramp instruction counts, and expandable connection gaps and source notes. Counts describe direction mentions, not distinct equipment or verified accessibility. Missing instructions leave accessibility unknown. A Barrier-free result mentioning stairs or escalators has an explicit caution. Comparisons relative to Recommended are omitted when it is unavailable; if source resolution changes the mapped endpoints, the card flags the difference instead of calculating a time/distance delta. Waiting times, closures, access hours, paid-area restrictions and wheelchair suitability are not independently verified.

Selecting another route changes the map and starts a new manual journey with no inherited floor confirmations. Changing endpoints or direction language clears alternatives and cancels pending work. Late responses cannot repopulate a replaced trip; requests have a 45-second client deadline. Successful results stay in component memory for the current planning session. Starting guidance unmounts the comparison; returning retains the selected route and can compare its alternatives again through the provider's existing short-lived cache.

Only the preferred profile and directions language are added to device preferences; routes and coordinates are not persisted there. Existing trips retain their explicit profile/language. The UI calls the official profile Barrier-free rather than implying a guaranteed step-free walk. A comparison uses the already selected concourse connection for fairness; choose a different mapped starting point or plan a new Barrier-free trip to resolve a new concourse connection under that profile.

## Continuous journey guidance

The planner, active walking card and route floor plans share one manual cursor through the complete government direction sequence. Continue opens the next instruction's city or indoor view; browsing maps and changing floors do not advance the journey. Returning from an indoor plan retains the current instruction. Starting or ending GPS guidance retains this cursor; a replacement route resets it and its floor confirmations.

An instruction links to an indoor venue only when it names exactly one available route venue. A floor link requires an unambiguous supplied venue/floor name, including Traditional Chinese names and the documented ground-floor aliases. A source lift, escalator, stair or ramp instruction between two instructions naming the same venue stays in that venue view, with no assigned floor. Other sections retain the city view and their original source text, including exits, malls, footbridges and streets; a city view does not imply an outdoor section. Missing indoor coverage preserves the full source sequence.

For a linked floor, the user opens its plan, checks signs and selects **I'm on [floor]** before Continue becomes available. The confirmation applies to the uninterrupted visit to that floor; a connector, a different floor, or another section requires a new confirmation when returning. Browsing another floor is never confirmation. GPS updates do not advance this cursor, confirm a floor, or complete the journey. The final Finish journey action is explicitly manual. These controls do not validate current access, lift operation or physical indoor positioning.

## Evidence boundaries

GPS fixes must have valid coordinates and arrive in timestamp order; delayed older callbacks cannot rewind guidance. Fixes expire after 30 seconds, while denied permission clears the fix immediately. A missing fix hides the location annotation and stops following without removing the route. A fresh accepted fix clears the signal error and resumes progress. Guidance, camera following and recalculation share a maximum reported accuracy of 60 metres (an application threshold, not proof of street-level accuracy). Poorer fixes show a dot and accuracy ring rather than a directional navigation arrow; the instruction and remaining-distance card wait for an adequate fix. These recovery paths have deterministic unit coverage; physical Android recovery remains unverified.

GPS does not establish indoor floor identity. Progress is an XY estimate over the returned route's actual segments, without joining disconnected paths. Source step distances approximately map progress to an instruction; this is not surveyed turn positioning. Direction uses a recent absolute compass or a moving GPS course. No heading is invented when neither exists. The textured city is an exterior model and is not evidence of current lift availability or indoor coverage.

## 3D presentation

3D remains the preferred view when configured, with a 2D switch in the planner. Map settings offers Clean buildings and Photo city. Choosing a style pairs Clean buildings with the standard raster and Photo city with aerial imagery; the background remains independently editable afterward. Clean buildings is the default when its authorised source is configured: official object-based building models stream over the basemap with a pale opaque material with soft normal-based shading and a muted raster basemap, with an outlined route overlay for contrast. It does not claim to supply interiors or infrastructure geometry. Photo city retains the original configured source and reveals actual loaded geometry progressively over the basemap. It no longer waits for the entire initial tile queue, which could keep a selected Photo city view flat on a slow connection. Partial coverage is still labelled as refinement; source holes are not repaired by this reveal policy. First rendered models and a settled request queue are separate measurements. Coarse parents are retained during refinement. During continuous GPS following, camera movement no longer suppresses pending tile requests. Standard resolution uses a 1× rendering scale instead of 1.25×.

`CityLayers` owns source-specific callbacks and resources. Switching styles leaves the camera and route untouched, hides the other source without destroying it, and shares one configured cache target across retained sources. Visible tiles can exceed cache targets. Source callbacks cannot overwrite another style's state. Failed tile traversals with no pending network or processing work report unavailable coverage rather than endless refinement. A later completed view clears that state. After 45 seconds of active loading without a completed tile, the view is marked slow and manual recovery becomes available. A completed tile resets this timer; hiding the source or disposing the scene cancels it. This is a quiet-loading heuristic, not a measured network timeout or evidence of server failure. Map settings offers Retry 3D loading while unavailable or slow; it disposes and reloads the selected source while preserving the renderer, route, camera and other style cache. The selected source cache is intentionally replaced on this explicit retry; no automatic retry loop is added. Disposal releases tilesets, shaders, listeners and request-budget leases, including late manifest results.

Route framing takes priority over selected places, fits above the mobile sheet, and does not move the follow camera when the sheet settles. The route is not rebuilt on GPS updates. The outlined overlay can show obscured route sections through buildings. This indicates route visibility, not an underground classification, and does not change source heights.

Replacing a route during guidance updates the geometry without requesting an overview camera flight. The GPS subscription and wake-lock lifecycle depend on an active trip with a route, rather than the route object identity. Recalculation therefore retains the current fix, while progress is recomputed against the new geometry and its crossing-history hint is reset. Reapplying the identical route and display options reuses its geometry. Returning to the planner preserves the route's profile and language.

Tile-progress events and the first coverage reveal explicitly request a frame, so stationary request-render scenes can advance without a camera gesture. This is a lifecycle correction, not evidence of a measured loading-time improvement. Mobile route summaries remain in the sheet while it is open; the floating summary appears only when the sheet is collapsed.

Clean buildings uses a coarser screen-space error of 128 for the first coverage pass before restoring the selected quality. Photo city uses the selected quality immediately, with Cesium skip-LOD and immediatelyLoadDesiredLevelOfDetail enabled: the inspected photo hierarchy contains replacement-refinement descendants, so desired-detail loading can bypass coarse ancestor payloads. Progressive reveal alone was rejected after the replay showed large blurry blocks at walking scale; the revised desired-detail policy produced textured Admiralty buildings while the remaining queue was still loading in the desktop replay. First visible geometry was reported at 13.3 seconds in that run, which is not complete coverage or a controlled speed comparison; verification across areas and physical devices remains required. The development replay reports loaded/unloaded tile counts, estimated tileset memory and time to first coverage; it does not expose provider URLs or credentials. These measurements distinguish a loading queue from cache eviction. A stationary browser sample showed 13 loaded tiles, 4.3 MiB and zero unloads while coverage was still preloading, so increasing cache capacity was not supported by that sample.

The selected 3D dimension is honoured before a destination is selected, rather than displaying a flat map under a 3D selector. The planner starts from the saved dimension preference. In 2D, opening the planner warms only the root manifest; model traversal starts when 3D is requested. First-coverage timing starts at that request, rather than including time spent entering a destination. A tested screen-space error of 512 reached first coverage in 52.8 seconds in one browser run, but produced visibly blurred buildings; it was rejected and is not the application setting. This is not a controlled speed comparison or an Android benchmark.

LandsD 3D requests use a host-scoped budget of six rather than Cesium's default 18. Overlapping renderers share the budget, stricter existing settings are preserved, and disposal restores the prior setting without overwriting a later owner. This keeps more waiting work in Cesium's camera-priority queue. It does not alter other provider hosts or promise faster startup on every connection.

The development replay accepts `model=clean` for the [official non-textured surface models](https://portal.csdi.gov.hk/csdi-webpage/apidoc/3d-visualisation-map-non-textured-models-api), `model=objects` for the [object-building API](https://portal.csdi.gov.hk/csdi-webpage/apidoc/3d-spatial-data-api), and `requests=4|6|12|18` for request-budget comparisons. The normal app's Clean buildings configuration uses the object-building API after visual comparison; the surface mesh looked too busy in dense streets.

A non-textured surface run with 18 requests had 41 tiles loaded at 59 seconds and completed-resource p95 about 51.3 seconds; a later six-request run had 68 loaded at 38 seconds and p95 about 9.0 seconds. These sequential samples do not control source/server/network cache conditions and do not prove a causal speedup. Later repeat loads of that same surface-model Admiralty view rendered models in 0.3–0.4 seconds and settled the first queue in 0.7–1.4 seconds in this browser. Those are warm-repeat observations, not cold-load or Android guarantees. The separate object-building cold trial first rendered models at 42.9 seconds. A later current-code desktop replay first showed geometry at 40.5 seconds with six network requests, zero processing, zero unloads and 5.5 MiB retained. Its browser cache conditions were uncontrolled; a subsequent repeat first showed geometry in 0.5 seconds. This supports investigating delivery/scheduling rather than raising cache capacity, but does not isolate server time or prove production startup performance. The local metrics aggregate durations without retaining URLs or query credentials. Pending network requests and model processing are reported separately. Request durations include browser queuing; they do not isolate government server time. Frame intervals from this development browser are not an Android frame-rate benchmark.

The original detailed source's root and sampled dependent manifest returned HTTP 200 in direct probes with inherited authorization. Both declared `no-store, no-cache`. Persistent browser disk caching must not be promised from these probes. Source mesh holes, missing textures and network outages cannot be repaired by raising the cache budget.

Official 3D URLs receive a stable, hashed application-origin cache variant. Direct probes found origin-specific CORS responses without a Vary header; a cached response from another local port could therefore be unsuitable. The variant preserved authorization and restored model rendering in the production localhost preview. It is not offline caching and does not override provider cache directives. Diagnostics redact resource URLs and credentials.

## Guidance lifecycle verification

React integration tests run in a test-only DOM environment with injected GPS callbacks and simulated time. They verify one GPS watcher and wake lock across route replacement, progress against replacement geometry, trip-end cleanup, poor accuracy, signal expiry/recovery and permission denial. Route-update integration checks verify failure/retry, retained routes, discarded late responses after trip end, timeout handling and malformed responses. Updates have a 20-second client deadline and retain the current route on failure. Validation details are not shown as navigation instructions.

Pending wake-lock requests are coalesced across repeated visibility events; a lock granted after trip end is released. These are lifecycle checks, not physical GPS, compass or Android frame-pacing measurements.

## Context labels — 17 October 2026

Navigate keeps a bilingual screen-label layer for the existing curated places and official MTR station reference points. It is independent of the planner's discovery-marker filtering. Place chips open the existing detail card; station chips open the existing station-map dialog, which reports unavailable indoor coverage rather than inventing a floor plan. Destination chips have highest layout priority. Raster road/address labels remain available in 2D. In 3D, upright place/station chips and subdued official vector street/building names replace raster text to avoid stretched text and mesh occlusion. Coverage depends on the source and collision layout.

The renderer projects label anchors above the mesh as screen annotations, not measured rooftop heights or indoor entrances. Rounded chips use 44px touch targets, a category icon, full accessible names and the selected map language. A greedy screen-space layout enforces gaps, viewport/sheet bounds and a maximum of 12 mobile labels or 20 desktop labels, with separate street, building and station limits and highest priority for the destination. Collision layout updates at most about six times per second; visible chip transforms follow renderer frames without React updates. During active walking guidance, larger discovery chips are hidden while quiet street/building names remain.

The overlay does not intercept pointer gestures. Canvas hit testing handles taps, so panning and pinching can begin over a label; keyboard activation uses actual buttons. Renderer disposal releases the frame listener and removes the overlay. Tests cover layout priority, collision limits, bilingual buttons, hit testing and disposal.

## Indoor mobile sheet and ambient map names

The indoor dialog has a fixed header with a 44px close control, an independently scrolling body, safe-area padding and header swipe-down dismissal on mobile. Floor markers are grouped in screen space with at least 48px between cluster anchors. Tapping a cluster zooms into its source points. Only points that still overlap at maximum zoom use a small dismissible chooser. Choosing a mapped point preserves its source coordinate, level and routing identity. Clustering does not assert physical connectivity. Long exit lists and point dropdowns are absent from the default viewer.

Ambient street and building names use the official LandsD Vector Map Label API, separate from the curated POI chips. The provider decodes `_name` fields from street centreline and building-name layers; house numbers and unrelated annotation layers are excluded. Road anchors are sampled along their source lines, without connecting disjoint line parts. Names are upright, subdued text above the 3D mesh and retain the requested English/Traditional Chinese language. Label density varies with the visible area and zoom; names can be omitted where they overlap or the source has no label. There is no guarantee that every building has a supplied name.

The renderer fetches a 3×3 neighbourhood of documented zoom levels 13–15 after settled camera changes, with two concurrent requests, cancellation, a 32-tile memory cache and a 12-second request deadline. Response reads are capped at 2 MiB. Failed publications impose a one-minute retry cooldown. Active navigation checks the camera area at five-second intervals, reusing unchanged tile keys; it keeps quiet street/building text while hiding larger discovery chips. No URLs or geographic data enter the preference store. The map retains the Lands Department credit.

Official source: https://portal.csdi.gov.hk/csdi-webpage/apidoc/VectorMapLabelAPI

### Indoor plans: buildings and MTR

Navigate → Indoor maps opens a searchable Buildings / MTR stations catalogue. Covered place and search-result cards also offer a direct indoor-map button when one official venue name matches exactly; geographic proximity never substitutes for a source venue ID. Building layers use the public `venue_polygon`, `level_polygon`, `amenity_point`, `unit_polygon` and `opening_line` services. Station layers retain their separate `mtr_*` services and cache keys. Requests are bounded, cached for six hours, and fetch detailed layers only for the selected venue. Fixture mode never substitutes live indoor requests.

The initial MTR floor is the supplied concourse when present, while buildings prefer a supplied ground-floor name. Each floor remains separate. Exit codes are visible on the diagram, alongside prioritised lift/toilet symbols. Tap Expand for the full-screen plan, use two-finger pinch or wheel/zoom buttons, and drag to pan. Fit restores the floor overview. Cluster taps zoom to their actual source coordinates; only inseparable points at maximum zoom open a local chooser. An expanded dialog retains a direct close button and a collapse control.

The plan camera updates a DOM transform during gestures and publishes the settled zoom to update screen-space grouping. Buttons retain 44px targets after zoom. Keyboard users have zoom controls and arrow-key panning. Browser page scrolling remains available outside the map; map gestures stay inside the indoor viewer. Pointer-pinch integration tests exercise the camera logic, but physical Android gesture performance remains a separate validation task.

Building floor plans are view-only: displayed boundaries and amenities do not establish permitted access or verified routing. MTR source-point routing remains available through selected point actions. The UI does not advertise a building route merely because its floor plan exists.

Official source: https://portal.csdi.gov.hk/csdi-webpage/apidoc/3d-indoor-map-api

### Clickable indoor entry points

Indoor maps is a full-width bordered action with an icon and chevron. Secondary text actions have a visible surface and border; route options retain a button-shaped disclosure control. Covered buildings get an Indoor map chip in Navigate mode at neighbourhood zoom, opening the venue dialog directly through the renderer's existing canvas hit test. ## Station-aware walking routes — 17 October 2026

Generic station references do not identify an entrance or floor. Selecting one as the origin now defaults to a labelled assumed concourse connection, with mapped point and current-location overrides. Source directions expose the selected connection. Destination references are labelled and offer an entrance/floor picker. Search station metadata is retained on route endpoints; older route names are matched exactly and near the known reference coordinate. No floor is derived from phone GPS.

The route overview retains every original edge but makes station-area geometry thin and muted, paired with a tappable station-section label and route card. Station sections are ordered along the journey. Exact station names in source directions also identify intermediate stations, not only endpoints; floor reads are serialized so selected-venue details retain source capacity. Aborted queued work is skipped. Opening one shows the named levels used by the route, Previous/Next level controls, selected-floor route arrows, generic up/down change markers and source instructions that explicitly name that floor. Continue beyond station returns to the city route overview; it does not imply that the next section is outdoors.

Floor association is geometric, not an authoritative floor ID from the solver. A segment needs compatible source Z at both ends and full containment in exactly one source floor. Ring intersections partition the entire segment so holes, concave gaps and disjoint polygons cannot be shortcut by endpoint/midpoint sampling. Ambiguous segments remain unassigned. A change in Z produces only a Level change marker, never an inferred stair/lift type. Actual lift/escalator wording is taken from the source directions, not attached to an assumed precise feature location.

Route inspection frames the relevant leg instead of the whole platform. The initial camera is used once per floor; late amenity loads and polling do not reset a user's pan. Indoor plans preserve pinch/drag and the direct fullscreen close control. Normal station browsing still prefers a supplied concourse; inspecting a route starts on its first matched floor. Matching does not verify access permissions, live lift operation, the user's floor, or alignment to the exterior city mesh.

City route fitting accounts for the narrower horizontal field of view on a portrait screen. Explicit sheet-state changes rebind obstruction measurements, and route cards retain their independent access to station detail when map labels are collision-hidden.

### Map-first indoor journey controls — 17 October 2026

Route floor plans open expanded. A shared City/station strip changes views without discarding the route, and the last manually chosen station floor is retained while the route remains unchanged. No view selection asserts that the user is physically at that station or level. A bottom action advances through mapped route floors; the last floor returns to the city. Secondary instructions and source limitations live in the options panel.

The indoor camera supports drag, pinch and two-finger twist with imperative DOM transforms. Floor changes preserve the user's rotation; map labels counter-rotate after the gesture settles. Compass alignment is explicitly requested, uses an absolute orientation reading when available, and aligns the map once. Unsupported or denied sensors leave manual rotation available. It does not provide an indoor location dot or automatic floor detection. Keyboard `[` / `]` rotates, `+` / `-` zooms, and arrow keys pan. North and fit controls remain accessible.

### Concourse defaults, route exits and building overlays

A generic station start no longer blocks planning on exit selection. The client explicitly requests an assumed concourse; the provider resolves that assumption to a real mapped concourse connection and source Z. It never creates an indoor coordinate from a floor centroid. Unsupported concourses fail with a request to choose a mapped point; barrier-free starts exclude stairs and escalators. The assumption stays visible and is not indoor positioning.

A route's last uniquely matched station floor can identify a recommended mapped exit only when an entry on that floor lies within 12 m of same-height route vertices. The exit is labelled on the city map and indoor plan. This is the route's recommendation, not proof of the globally closest exit, fare-gate access or current opening status.

Named intermediate buildings now use the same floor matching as stations. Opening any available building while a route exists also attempts local matching against its floor polygons and source Z, selecting a matched route floor by default. Missing/ambiguous matches remain explicitly unavailable; no route is projected onto an unrelated floor. City overview framing points from the route's start toward its destination rather than resetting north.
